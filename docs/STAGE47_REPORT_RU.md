# The Story of Thor 2 — Stage 47: сверка производителя и отправителя дескрипторов VDP1

Дата: 22.10.2026. Это этап **повторной проверки ранее найденного производителя**, а не утверждение о новом динамическом захвате. Stage 46 прошёл CI GitHub Actions №39694271027. Оригинальный ISO остаётся приватным.

## Почему важно повторно использовать Stage 16

Stage 16 уже нашёл кандидатный участок, который создаёт 8-байтные дескрипторы (поля +0/+4/+6), увеличивает общий счётчик на единицу, продвигает указатель на восемь байт и сравнивает счётчик с литералом 512. Stage 17 искал вызовы этого участка, но не нашёл их узкими прямыми эвристиками. Stage 45 восстановил 32-байтный копировщик в VRAM VDP1; Stage 46 — его управляющий шлюз. Раньше два результата о производителе и шлюзе не сверялись строго между собой.

## Что теперь проверяет новый инструмент

tools/stage47_vdp1_producer_reconciliation.py на приватном 0TH2.BIN выполняет:

1. Независимый поиск полного шлюза Stage 46 и кандидатного производителя Stage 16.
2. Сравнение **трёх** адресных опор шлюза со значениями Stage 15: начала буфера, общего счётчика и ячейки указателя. Совпадение лишь части опор не объявляется связью.
3. Дополнительную проверку, что BT после сравнения счётчика с литералом 512 перескакивает хотя бы локальное приращение указателя. Прежний анализ Stage 16 проверял наличие BT, **но не вычислял его фактическую цель**.
4. Ограниченный поиск синтаксических MOV.B Rm,@Rn после PC-relative загрузки адреса флага, с отдельным подсчётом сброса в шлюзе и других кандидатов. Отрицательные непосредственные значения учитываются только при наблюдаемом MOV #imm,Rm без промежуточной перезаписи.
5. Аналогичный подсчёт непосредственных MOV.W-записей счётчика и строгой цепочки MOV.W @R3,R1; ADD #1,R1; MOV.W R1,@R3.

Результат — только агрегированная JSON-метаинформация; в ней нет RAM-адресов, исполняемых байтов, оригинальных смещений или игровых материалов. В публичном CI используются исключительно синтетические данные.

## Ограничения выводов

Условие сравнения count >= 512 и локальная цель BT **не доказывают** безопасность всех путей доступа к буферу. Три совпадающих адреса и найденные последовательности записи дают статическую цепочку-кандидат, но не доказывают тождество всех вычисляемых указателей, выполнение кода или управление игровым состоянием. Возможны записи через другие режимы адресации, косвенные вызовы и другие производители.

Особенно важно сохранить открытым вопрос Stage 16/17: производитель прибавляет к количеству дескрипторов единицу, но поле количества 32-байтных команд строится посредством сдвига аргумента вправо на три бита. Необходимо установить реальные допустимые значения аргумента, прежде чем объявлять этот учёт согласованным.

## Статус в публичной ветке

Реализация + синтетические unit-тесты подготовлены. **Повторный запуск на оригинальном ISO в этой сессии не проводился**, поэтому числа по нему в данном отчёте не приводятся. Перепроверка интеграции через GitHub CI и конкретный прогон оригинального образа — отдельные свидетельства.
