# The Story of Thor 2 — Stage 109: SH-2-наблюдатель в исходном коде Mednafen

## Проблема

Stage 107 дал реальные SH-2 debugger-кадры после чтения системного указателя; Stage 108 независимо подтвердил назначение интерфейса `SYS_CHGSCUIM`, но новая автоматическая остановка была поставлена слишком поздно. GUI-скрипты XTest нельзя считать воспроизводимой записью всех последовательных инструкций или доказательством возврата BIOS-функции.

## Новая реализация (публичные данные)

Добавлен `tools/stage109_patch_mednafen_observer.py` — строго ограниченная инструментирующая правка **общедоступного исходного кода** Mednafen 1.29.0 (`src/ss/ss.cpp`). Она добавляет наблюдение регистра R13 и контрольных регистров процессора непосредственно до и после очередного SH-2 шага. Исходные данные не нужны при сборке. Наблюдатель по умолчанию **отключён**.

Интерфейс активации только для последующего **приватного** запуска:

- `STAGE109_SH2_OBSERVER_ENABLE=1` — явное разрешение;
- `STAGE109_SH2_OBSERVER_PC` — восьмизначный адрес инструкции, передаваемый локально при запуске;
- `STAGE109_SH2_OBSERVER_OUT` — путь к приватному файлу трассы;
- `STAGE109_SH2_OBSERVER_MAX_STEPS` — максимум шагов (4–4096, по умолчанию 256).

При совпадении триггера с PC_ID/PC_IF/RPC начинается bounded-захват до/после шагов: значения PC, R13, PR, R2–R6. Сырые значения **сохраняются только на локальный приватный диск**, никогда в стандартный вывод GitHub Actions. Наличие трассы само по себе не подтверждает неизменность эмулятора и полную идентичность целевой функции — требуется отдельный независимый ABI- и BIOS-анализ.

Девять синтетических unit tests и отдельная C++11 проверка синтаксиса набора полей выполнены локально. Тесты проверяют отсутствие захардкоженных приватных адресов/путей, opt-in, границу размера захвата, точную привязку к CPU Step, отказ от повторного патча и неузнаваемой версии источника.

## GitHub Actions

В `.github/workflows/stage109-public-sh2-observer.yml` создан workflow: Ubuntu 24.04 скачивает **только открытые исходники Mednafen через штатный Ubuntu source package**, запускает синтетические тесты, накладывает патч и собирает исполняемый файл, который загружается как **краткоживущий публичный артефакт**.

Ни ISO, ни BIOS, ни приватные PC, ни скриншоты не передаются GitHub Actions. Пока workflow не выполнен успешно на точном head PR, **новый бинарник нельзя считать полученным или работоспособным**.

## Дальнейшая работа — Stage 109 runtime gate

1. Дождаться положительного CI, проверить SHA-256 полученного публичного бинарника, устранить возможные ошибки его сборки.
2. Локально с ранее проверенными ISO и BIOS запустить два отдельных сеанса с приватным адресом триггера Stage 107. Зафиксировать настоящий переход на косвенный вызов, вход, возврат и R13 (при условии, что триггер действительно достигается).
3. Не делать заявлений о сохранении R13 до подтверждения точной call/return-пары; отличать ранний BIOS-вызов от позднего writer Stage99.
4. Неизменённые сырые трассы хранить на Google Drive в `02_Raw_Traces_and_Captures`, SHA-256 в `00_Manifest_and_SHA256`, безопасный агрегат в `03_Aggregate_Reports`, логи в `04_Logs_and_CI` и приватный handoff в `05_Handoff_and_Stage_Notes`.

**Текущее доказательство:** инструментирование готово как исходный код и прошло локальные синтетические проверки; новая реальная трасса и безусловное сохранение R13 пока **не подтверждены**.
