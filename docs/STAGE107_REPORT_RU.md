## Проверка подготовленного образа / CUE

На закреплённом оригинальном ISO повторно выполнен Stage54 preflight: дисковый регион E, 52224 cooked MODE1/2048 секторов, согласованный boot/first-read layout; подготовлен отдельный **временный** CUE для однотрекового MODE1/2048 представления. Существующие отсутствующие CD-DA дорожки или subchannel-данные этот CUE не восстанавливает. Внешний Saturn BIOS и исполняемый файл эмулятора не найдены, запуск Saturn не выполнялся, реальных RAM/VRAM/SH-2 трасс пока нет.

Приватные Stage107 CUE (в 07_Builds_and_Test_Artifacts), JSON preflight (в 03_Aggregate_Reports) и его SHA-256 манифест (в 00_Manifest_and_SHA256) сохранены в Google Drive. Загруженные копии повторно скачаны: все три SHA-256 совпали, папки и права владельца проверены.

## Что реализовано

`tools/stage107_private_runtime_slot_witness.py` — офлайновый fail-closed анализатор для двух приватных независимых захватов. Он НЕ открывает ISO/BIOS и никогда не печатает адреса, содержимое регистров или сырые события.

Контракт: обязательные исходный ISO SHA-256/размер, сборка эмулятора, внешний оригинальный BIOS региона E с закреплённым SHA-256, две SHA-256-связанные записи событий с разными session IDs. Для каждого вызова необходимо собрать **упорядоченную тройку**:

1. `slot_read`: перед косвенным вызовом считать из указанной low-memory ячейки фактическую цель указателя; зафиксировать SH-2 PC, регистр R13 и цикл.
2. `call_entry`: до исполнения target зафиксировать вход и R13.
3. `call_return`: после возврата зафиксировать R13, PC и цикл.

Все приватные поля `cycle`, `call_id`, `slot_address`, `caller_pc`, `target_address`, `r13` должны быть согласованы. В коде реализованы проверки exact-schema, монотонных циклов, одинаковой цели в рамках пары, совпадения entry/return R13, сохранности SHA-256 входных файлов, отсутствия повторяющихся ключей, разных ID сессий, строгого отказа для HLE BIOS.

Наличие даже **идеальных** структурно согласованных JSON не аутентифицирует работу эмулятора: оператор может изготовить такой JSON. Поэтому выход **всегда** оставляет:
- `runtime_execution_independently_authenticated=false`
- `runtime_target_independently_identified_as_sys_chgscuim=false`
- `specific_bios_r13_preservation_independently_proven=false`

Даже при совпадении сохранения R13 в захватах нужно отдельно идентифицировать целевую BIOS-функцию и установить происхождение событий от настоящего инструментированного ядра.

## Локальная регрессия

12 синтетических тестов прошли. Они покрывают успешную согласованную искусственную пару без runtime-claim, повреждённый хеш, неправильный ISO, HLE, одинаковые сессии, разные цели, модифицированный R13, нарушенный порядок циклов, неверный call ID, дубликаты JSON-полей, недопустимые приватные поля и неразглашение сырых значений в безопасных ошибках. **Это не реальный игровой захват.**

## План получения реальных данных

1. Законным способом получить приватную BIOS для дискового региона E и верифицировать её локально по официальному SHA-256; проверить точную архитектуру/версию исполняемого эмулятора.
2. Убедиться, что оригинальный cooked ISO (MODE1/2048) действительно загружается с подготовленным Stage54 CUE. Примечание: исходный образ не содержит проверенную полную раскладку CD-DA дорожек.
3. Через PC/read breakpoint в debugger или инструментированный SH-2 observer получить **два реальных и независимых** запуска с журналированием slot-read, фактической indirect JSR цели, входа/возврата и R13. Штатный GUI debugger Mednafen сам по себе не обещает автоматическую выдачу требуемого JSON.
4. Сохранить необработанные трассы без изменений в `02_Raw_Traces_and_Captures`. SHA-256 манифест и версию collector — в `00_Manifest_and_SHA256`; безопасный агрегат — в `03_Aggregate_Reports`. Проверить Drive readback.
5. Только после независимой аттестации происхождения и BIOS symbol/ROM-привязки обсуждать повышение статического вывода Stage104 в runtime proof.

Публичный GitHub — только код, синтетические тесты и безопасная документация. Синтетические фикстуры не считаются доказательством игры.

## Реальный запуск Saturn с оригинальным образом: подтверждена загрузка до титульного экрана

После уточнения пользователя европейская BIOS найдена в приватной папке другого Saturn-проекта. Её размер — 524288 байт; SHA-256 — 96e106f740ab448cf89f0dd49dfbac7fe5391cb6bd6e14ad5e3061c13330266f, **точное совпадение с официальным эталоном NA/EU Mednafen**. В 01_Private_Originals создана отдельная приватная копия; SHA-256 после Drive readback совпадает, права — только владелец.

Через GitHub Actions #40032076606 получен открытый бинарник Mednafen 1.29.0 и необходимые публичные библиотеки (без BIOS или игровых данных). SHA-256 бинарника: 3bdba278610b49ca6de0b8d4c5b210b33c750d3978bf8246cc4cb0123a7f458f. Stage54 повторно прошёл при наличии подлинной BIOS региона E.

Mednafen успешно открыл приватный MODE1/2048 CUE, распознал модуль Saturn ss, идентификатор диска MK-81302, название The Story of Thor 2 и область E; начал работу аудио- и видеосистемы. В двух реальных локальных сессиях были получены кадры заставки Ancient и титульного экрана The Story of Thor 2. Последующий кадр полностью чёрный. Нажатие START предварительно опробовано, но переход к игровому процессу и работоспособность управления не подтверждены.

Подлинные PNG-кадры и исходные журналы Mednafen помещены соответственно в закрытые 02_Raw_Traces_and_Captures и 04_Logs_and_CI; агрегат в 03_Aggregate_Reports, SHA-256 manifest в 00_Manifest_and_SHA256. Семь файлов выгружены из Drive и проверены побайтно, дополнительно сохранены BIOS preflight и его manifest. Ни одна прошивка, игровой кадр или игровой образ не опубликованы в GitHub.

Граница результата: запуск до титульного экрана подтверждён локальным исполнением. Но **реальный service-slot target, идентичность SYS_CHGSCUIM, сохранение R13, исполнение SET07 и игровой процесс пока не доказаны**. Для них требуется инструментированный SH-2 observer и два независимых приватных трассировочных захвата.

## Реальная адресная остановка SH-2: Stage107 debugger service-slot milestone

В штатном отладчике Mednafen 1.29.0 программно через XTest открыта CPU debugger-панель. Адрес общей системной ячейки независимо реконструирован Stage100 на приватном оригинальном ISO; только приватный ввод содержит сам адрес. Для ячейки установлен read-breakpoint. **Точка действительно сработала на инструкции SH-2**, после чего выполнен ровно один шаг и наблюдалась загрузка указателя в регистр цели.

Два независимых локальных запуска дали побайтно одинаковые кадры отладчика непосредственно после шага SH-2. Кадры до/после, исходные журналы двух сессий, приватный скрипт-коллектор, входной адрес и подробный SHA-256 manifest сохраняются в соответствующих каталогах Project Evidence Archive, чтение из Drive подтвердило неизменность всех десяти файлов и права owner-only.

Событие наблюдалось **в ранней фазе загрузки**, не на позднем writer Stage99. Оно подтверждает реальный доступ через уже исследованный slot и исполнение инструкции чтения. Само по себе оно **не доказывает** точную идентичность прочитанной функции как SYS_CHGSCUIM, возврат этой функции, сохранение R13 в позднем Stage99 call site или прохождение игры. Отдельный machine-readable observer SH-2 для регистров/целевого вызова по-прежнему необходим.
