# The Story of Thor 2 — Stage 28: ненулевая ветка вложенной структуры

Дата: 21.10.2026. Приватно исследован оригинальный Sega Saturn ISO MK-81302; SHA-256 `25b0b2774d4621bd9f95a01fc5420ded37b481b61b3cdf515360d82b2cb7bb0d`. В публичном GitHub нет образа, оригинальных машинных байтов, точных файловых адресов, текстур или звука.

## 1. Общая схема

После проверки на отсутствие вложенного указателя вспомогательная функция выполняет отличающийся от очистки Stage 27 путь подготовки семи байтов исходной структуры по смещениям `+31…+37`. Значения считываются из вложенного источника через `R4` с добавлением отдельно вычисленного 32-битного смещения из локального стека. Это не доказательство формата пикселей.

Инструкция `EXTS.B R6,R0` и `CMP/EQ #3,R0` выбирает порядок первых двух байтов. `BT/S` использует обязательный слот задержки с `ADD R3,R4`; добавление смещения к указателю выполняется **на обеих ветках**.

| Условие | Порядок первых двух записей |
|---|---|
| Знаковый байт R6 равен 3 | `+32`, затем `+31` |
| Иное значение | `+31`, затем `+32` |

Обе последовательности сходятся в одну точку. В альтернативной ветке обычный `BRA` пропускает специализированный путь; его слот задержки выбирает позицию `+32` для последней записи. Цели переходов проверяются вычислением PC-relative смещений, а не только сопоставлением байтов.

## 2. Остальные поля

После объединения веток источник последовательно даёт значения для `+33` и `+34`. Далее обнаружены `SHLL` и байтовая запись `+35`; отдельно второй `SHLL` и **16-битная запись** в `+36…+37`. Эти сдвиги удваивают значение в регистре перед усечением при записи; они не обязательно означают удвоение размеров изображения. Для отрицательных значений после знакового расширения важно различать размер регистра и ширину конечной записи.

## 3. Два независимых условных преобразования

Два 16-битных поля по смещениям `+88` и `+90` от исходной структуры сравниваются с одним PC-relative литералом `0x0100` (256). Если соответствующее поле равно 256, ветка `BT` пропускает группу дополнительных преобразований. Если значение другое, вызывается одна и та же функция через `JSR @R13`.

| Группа целевых полей | Проверяемое поле | Условие пропуска | Число вызовов JSR в группе |
|---|---:|---|---:|
| `+31`, `+32` | `+88` | равно `0x0100` | 2 |
| `+33`, `+34`, `+35`, `+36` | `+90` | равно `0x0100` | 4 |

Итого в исполняемом участке шесть статических точек `JSR @R13`; **это не значит, что все шесть выполняются при каждом вызове**. В слотах задержки `JSR` читаются соответствующие байтовые, а для последнего поля — 16-битные аргументы из исходной структуры. Возвращённые значения перезаписывают соответствующие поля.

Полную арифметику вызываемой функции `R13` и смысл специального значения `0x0100` нужно установить отдельно. Нельзя уже сейчас интерпретировать `0x0100` как формат текстуры, ширину спрайта либо флаг прозрачности.

## 4. Проверки и границы

- Локальная проверка на оригинальном `0TH2.BIN`: одна полная согласованная последовательность ненулевой ветки, связанная с ранее подтверждённым общим путём очистки.
- `tools/stage28_helper_nonzero_fields.py`: статический анализ двух маршрутов байтов, сдвигов, проверок литерала, целей переходов и групп косвенных вызовов, с выводом только агрегированных сведений.
- `tests/test_stage28_helper_nonzero_fields.py`: 24 синтетических сценария на корректную последовательность и повреждённые переходы, слот задержки, sentinel, записи и косвенные вызовы. GitHub Actions не получает оригинальный ISO.

Детектор проверяет узкие последовательности SH-2, а не весь граф исполнения и не реальные значения памяти в Saturn-эмуляторе. Поля `+31…+37`, `+88`, `+90` — **смещения внутри входной структуры**, не расположения внутри ISO.

## 5. Приоритет следующего этапа

Проследить, как задаётся адрес вызова `R13`, что именно делает единая вспомогательная функция преобразования и как результат относится к 8-байтовым дескрипторам VDP1. После этого проверять соответствие полей ресурсам `P0–P3` и только затем строить подтверждённый декодер графики.
