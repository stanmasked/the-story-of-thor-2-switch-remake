# The Story of Thor 2 — Stage 93: аудит общего загрузчика и старта SET07

## Источник и приватность

Оригинальный ISO обработан локально из приватной рабочей среды. Анализ использует корневые файлы 0TH2.BIN, TH2.LOW и SET07.BIN. ISO, извлечённые данные, адреса RAM, смещения инструкций и исходные байты в репозиторий не добавлялись.

## 1. Внутренняя структура общего loader-wrapper

Вызов из TH2.LOW и потребитель таблицы SET00–SET06 сходятся на одной функции-обёртке в основном исполняемом файле. Внутри неё обнаружены два последовательных вызова внутренних helper-ов.

- После первого вызова результат из R0 сохраняется в R14 и проверяется на неотрицательное значение через CMP/PZ.
- При отрицательном результате выполняется вызов общего error-helper-кандидата с аргументом-кодом 1. В ограниченном статическом потоке после этого вызова следующий участок снова ведёт к подготовке второго helper-а; локального раннего возврата в этом месте нет.
- Второй helper получает результат первого в R4, сохранённый аргумент назначения в R6, нулевое значение в R5 и -1 в R7. Точная семантика этих аргументов ещё не доказана.
- Результат второго вызова также проверяется на неотрицательное значение. При отрицательном результате вызывается тот же error-helper-кандидат с кодом 2.
- После второго участка функция возвращает значение второго helper-а через R0.

Эта структура показывает два этапа обработки результата и общую ветвь сообщения об ошибке. Она сама по себе не доказывает, что helper-ы выполняют именно открытие и чтение файла. Также неизвестно, возвращается ли error-helper нормально во всех runtime-сценариях.

## 2. Caller всё ещё не проверяет итог перед entry-call

Вызов обёртки для SET07.BIN в TH2.LOW по-прежнему непосредственно сменяется загрузкой того же буфера в R3 и JSR через него. Между возвратом обёртки и entry-call нет явной проверки её итогового результата.

Таким образом, внутренние проверки обёртки не эквивалентны проверке успешности загрузки вызывающей стороной. Если error-helper возвращается, статический поток продолжает выполнение; runtime-поведение при ошибке остаётся открытым.

## 3. Начальный код SET07.BIN

- Entry stub загружает указатель стека из literal, находящегося внутри диапазона самого модуля, затем вызывает внутреннюю стартовую процедуру.
- Стартовая процедура имеет распознанный пролог.
- До дальнейшей инициализации выполняются две ограниченные байтовые петли: очистка области и копирование байтов между областями модуля.
- Затем код вызывает внутренний helper и опрашивает другую внутреннюю процедуру в цикле. Возвращаемое значение знаково расширяется, проверяется маской 0x40, а вызов повторяется, пока этот бит не установлен.

Тест маски 0x40 — это проверка бита возвращаемого значения, а не доказательство callback ID 64. По одному этому циклу нельзя подтвердить регистрацию callback или service-slot; поэтому анализатор намеренно не выставляет такой признак.

## Реализация и проверки

Добавлен tools/stage93_loader_wrapper_and_set07_entry_audit.py и 7 синтетических тестов. Анализатор проверяет форму wrapper-а, две проверки результата, общую error-helper-цель, продолжение после error-call, возврат второго результата и начальную структуру SET07.BIN. Вывод содержит только агрегированные признаки и не раскрывает адреса.

Все 47 тестов текущего локального набора проекта прошли; compileall завершился без ошибок. Повторный анализ оригинального ISO подтвердил общий loader-wrapper, оба внутренних helper-call, две проверки результата, error-коды 1 и 2, отсутствие проверки результата вызывающей стороной и внутренний mask-poll цикл SET07.

## Следующий этап — Stage 94

1. Проследить тела двух внутренних helper-ов и общий error-helper по ограниченным CFG и другим callsite-ам, не приписывая им семантику open/read без доказательств.
2. Установить, возвращается ли error-helper после ошибок и как это влияет на последующий entry-call.
3. Сопоставить mask-poll SET07 с уже найденными callback/service-slot структурами; не отождествлять маску 0x40 с callback ID 64.
4. Продолжать отделять статические признаки от runtime-подтверждения.

**Границы вывода:** подтверждены статическая структура wrapper-а и начального кода SET07. Не подтверждены фактическая загрузка файла во время игры, семантика helper-ов, поведение error-helper при ошибке, callback/service-slot регистрация, runtime-исполнение overlay, DMA completion или синхронизация графики в одном кадре.
