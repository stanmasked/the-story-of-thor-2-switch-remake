# The Story of Thor 2 — Stage 73: путь передачи данных callback ID 64

## Цель

Продолжить Stage 72 и определить, какой путь выбирает вспомогательная функция после вызова callback ID 64: обычное копирование CPU или специальный обработчик видеопамяти. Оригинальный ISO прочитан локально; в репозитории находятся только анализатор, синтетические тесты и агрегированный отчёт.

## Результат статического анализа

### 1. Поле длины и поле submit gate — разные слова

Callback читает знаковое 16-битное слово, затем формирует длину:

`length = sign_extend_16(field) × 32 + 2`

Два сдвига на 2 бита, один сдвиг на 1 бит и прибавление 2 в delay slot перед вызовом подтверждают эту формулу. В этом локальном фрагменте нет проверки верхней границы значения.

Уточнение к предыдущим этапам: поле, из которого callback берёт длину, расположено непосредственно перед отдельным 16-битным счётчиком submit gate. Это соседние поля, а не один и тот же счётчик. Нельзя использовать проверку ненулевого счётчика submit gate как доказательство корректности длины, передаваемой callback-у.

### 2. Для фактических аргументов выбирается не CPU memmove

Внутри вспомогательной функции найдены проверки диапазонов адресов. Для пары «исходный буфер в рабочей RAM → база VDP1 VRAM» управление выбирает специальный путь с состоянием передачи, а не отдельную байтовую функцию memmove.

На этом пути статически подтверждены:
- установка глобального флага состояния в значение 1;
- запись адреса назначения и вычисленной длины в два глобальных поля;
- проверка адреса назначения на попадание в основной диапазон видеопамяти;
- два последовательных вызова внутренних обработчиков.

Отдельная generic-функция memmove также идентифицирована. Она сравнивает исходный и конечный адреса, возвращается при совпадающих указателях и нулевой длине, а для копирования использует прямой или обратный байтовый цикл. Но **аргументы callback ID 64 не выбирают этот путь**.

### 3. Специальный путь связан с обработчиком SCU DMA

Второй внутренний обработчик содержит ссылки на регистровый блок SCU DMA и диспетчеризацию к трём функциям внутри исполняемого файла. В документации Sega Saturn Developer's Manual адресный блок `0x25FE0000–0x25FE0017` соответствует регистрам DMA Level 0; регистр `+0x10` используется для включения/запуска передачи. См. [SCU DMA register details](https://docs.exodusemulator.com/Archives/SSDDV1R1E/a/a04/hon/p040.htm) и [SCU register list](https://www.infochunk.com/saturn/segahtml_en/hard/scu_/hon/p03_01.htm).

Это подтверждает, что специальный путь связан с SCU DMA, но не доказывает, что DMA реально запускается или завершается во время игрового кадра. Следующий этап должен проследить три внутренних обработчика и подтвердить точные записи в регистры, порядок запуска и сигнал завершения.

## Ограничения и важная несогласованность

- Runtime-вызов callback ID 64 и реальное исполнение передачи не подтверждены трассой.
- Точные записи в SCU DMA-регистры, выбранная ветвь диспетчера и подтверждение завершения передачи ещё требуют проверки.
- Длина формируется как `32 × signed_word + 2`, тогда как Stage 69 описывает резервирование четырёх байтов для END-маркера. Пока не доказано, что эти два механизма относятся к одному и тому же буферу, поэтому расхождение оставлено открытым.
- Локальная последовательность не ограничивает верхнюю границу поля длины. Необходимо найти и подтвердить upstream-инвариант до моделирования этого пути в ремейке.
