# The Story of Thor 2 — Stage 61: кадровый буфер VDP1 и первый нативный C++17 модуль

Дата: 22 октября 2026 года.

## Цель

Stages 45–60 восстановили статический путь заполнения команд VDP1, форматы текстур, правила прозрачности, режимы CRAM и кандидатов приоритетов/теней VDP2. Но важно разделять три разных объекта:

1. **VDP1 VRAM, 524288 байт**: команды, графические texel-блоки, LUT, Gouraud.
2. **VDP1 framebuffer, две независимые области по 262144 байта**: одна используется для рисования, другая для отображения. CPU-доступна только рисуемая сторона.
3. **Изображение после VDP2 compositor**: учитывает приоритеты, слои, палитры, тени, окна и цветовое смешивание и **не равняется** дампу VDP1 framebuffer.

Первоисточники Sega:

- [VDP1 User's Manual, 4.1 TVMR](https://www.infochunk.com/saturn/segahtml_en/hard/vdp1/hon/p04_11.htm) — ровно пять допустимых режимов и геометрия 256-КиБ кадрового буфера.
- [VDP1 User's Manual, 4.2 FBCR](https://www.infochunk.com/saturn/segahtml_en/hard/vdp1/hon/p04_12.htm) — автоматическое и ручное переключение и допустимые сочетания VBE/FCM/FCT/DIE.
- [VDP1 User's Manual, 2.1 framebuffer](https://www.infochunk.com/saturn/segahtml_en/hard/vdp1/hon/p02_11.htm) — пара буферов, доступность стороны рисования, 8/16-битные значения пикселей.

## Реализация

Создан `tools/stage61_vdp1_framebuffer.py`:

| TVMR | Название | Размер framebuffer | Бит/пиксель |
|---:|---|---|---:|
| 0 | normal | 512 × 256 | 16 |
| 1 | high resolution | 1024 × 256 | 8 |
| 2 | rotation 16 | 512 × 256 | 16 |
| 3 | rotation 8 | 512 × 512 | 8 |
| 4 | HDTV | 512 × 256 | 16 |

Отвергаются недопустимые режимы TVMR 5–7, зарезервированные биты, противоречивые VBE/FCM/FCT и запрещённое double-interlace в режимах 2–4. Входным объектом является **32-байтное зеркало записи регистров VDP1**, а не якобы достоверный прямой дамп регистров: реальные TVMR и FBCR документированы как write-only.

После проверки ровно 262144 байт рисуемого framebuffer Python-анализатор классифицирует 16-битные коды как: нулевой прозрачный, кандидат RGB555 (бит15=1), кандидат палитрового или служебного кода (бит15=0). Для 8-битных кодов отмечается только нулевая прозрачность либо индекс/служебный код; результат нельзя трактовать как окончательный цвет без SPCTL и CRAM. Отчёт сохраняет только **агрегированные количества**, без отдельных пикселей и адресов.

Важно: **дамп CPU-accessible кадрового буфера — это сторона рисования, а не подтверждённая картинка на телевизоре**. Даже сведения FBCR не доказывают момент аппаратного переключения без привязки к полям/кадрам.

## Начало нативного графического кода

Добавлен `native/vdp1_framebuffer.hpp` — независимый от SDL/libnx **C++17** модуль, который реализует те же базовые соглашения геометрии и считывания 8-/16-битных пикселей из приватного массива. Код не содержит ни одного пикселя оригинальной игры и переносим как на Linux/macOS, так и на будущую среду Nintendo Switch с devkitPro.

`native/tests/vdp1_framebuffer_test.cpp` содержит тесты всех пяти режимов TVMR, FBCR, последнего пикселя, длины буфера, верхнего бита RGB555, несочинения RGB для индексных данных и границ координат. В GitHub Actions добавлена отдельная job `native-framebuffer-host` с жёсткой компиляцией `-std=c++17 -O2 -Wall -Wextra -Werror -pedantic` и запуском тестового бинарного файла на хосте. Это **не сборка Switch NRO**.

## Команда исследования

```sh
# Только проверка приватного исходного ISO — без игровых кадров
python tools/stage61_vdp1_framebuffer.py \
  --iso-private "/private/The Story of Thor 2.iso"

# Только после реального синхронного захвата CPU-доступного DRAW буфера и зеркала TVMR/FBCR
python tools/stage61_vdp1_framebuffer.py \
  --iso-private "/private/The Story of Thor 2.iso" \
  --draw-framebuffer-private "/private/capture/vdp1-draw.private-framebuffer" \
  --vdp1-register-mirror-private "/private/capture/vdp1-write-register-mirror" \
  --output-private "/private/capture/stage61.private-fb-audit.json"
```

Приватный файл результата создаётся с правами 0600, без перезаписи или следования по симлинкам. Регистр-миррор должен быть получен из реального эмулятора как отслеженные записи или внутренние значения эмулятора; попытка прочесть write-only регистр из адресного пространства CPU не является надёжным источником.

## Тесты и ограничения

Добавлено **40 синтетических Python-тестов** и самостоятельный C++17 host-test: допустимые режимы и буферы, битовые значения, read-only/CPU-access ограничения, границы, приватность. Тесты не используют оригинальную игру или аппаратные снимки.

На текущий момент нет работающего Saturn-эмулятора, подтверждённого видеозахвата, VDP1 framebuffer или Nintendo Switch NRO. Следующий практический этап — независимая проверка реального запуска эмулятора с захватом **DRAW framebuffer, VDP1 TVMR/FBCR mirror, VDP1 VRAM, VDP2 CRAM и регистров** из согласованной точки кадра. Параллельно разумно начать чистый оригинально-ресурсный нативный графический прототип — с собственными тестовыми фигурами и управлением, без защищённых игровых спрайтов.
