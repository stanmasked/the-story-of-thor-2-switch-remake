# The Story of Thor 2 — Stage 32: прямые и косвенные вызовы трёх потребителей полей

Дата: 21.10.2026. Исследован локальный оригинальный Sega Saturn ISO MK-81302, SHA-256 `25b0b2774d4621bd9f95a01fc5420ded37b481b61b3cdf515360d82b2cb7bb0d`. Публичный отчёт не содержит байтов исходного исполняемого файла, точных позиций инструкций, исходного ISO или защищённых ресурсов.

## Найденные связи

На Stage 31 были распознаны три процедуры с чтением полей `R4+31…R4+34`, одна также читает байт `+35` и 16-битное слово `+36…+37`. Stage 32 вычисляет адреса их прямых SH-2 `BSR` (знаковое 12-битное смещение относительно PC+4), а косвенные вызовы устанавливает через `MOV.L @(disp,PC),Rn`: четырёхбайтовое выравнивание PC, 32-битный литерал и последующий `JSR @Rn`.

| Процедура | Прямые BSR | PC-литеральные JSR | MOV R14,R4 в слоте задержки | Особенность |
|---|---:|---:|---:|---|
| Первая (бит `R4+6`, `0x04`) | 1 | 0 | 1 | Аргумент подаётся R14 непосредственно перед входом |
| Вторая (бит `R4+7`, `0x01`) | 1 | 0 | 1 | Аргумент подаётся R14 непосредственно перед входом |
| Третья (все семь байтов) | 0 | 8 | 7 | Ещё один вызов задаёт `R5=2` в слоте задержки |
| **Итого** | **2** | **8** | **9** | 10 статических вызовов |

Семь из восьми косвенных вызовов третьей процедуры имеют последовательность «загрузка адреса в R3/R2 → JSR через этот регистр → MOV R14,R4 в слоте задержки». Последний использует последовательность «MOV.L литерал в R3 → ADD #-4,R15 → сохранение R4 → JSR @R3 → MOV #2,R5 в слоте задержки». В этом варианте **адрес, уже находящийся в R4, не восстановлен по происхождению**.

## Границы статического доказательства

- Вычисленные назначения переходов и загруженных из литералов адресов совпадают с точками входа трёх найденных процедур. Это гораздо более конкретное подтверждение их использования, чем простое сходство смещений полей.
- Однако сканирование исполняемого файла не заменяет полную проверку достижимости: какой именно игровой режим приводит к выполнению конкретного вызова, пока неизвестно.
- `MOV R14,R4` в слоте задержки показывает значение **регистра-источника** непосредственно при передаче управления, но не раскрывает происхождение указателя R14 у самого вызывающего кода.
- Наличие одного адреса вызываемой функции в нескольких литералах не доказывает одинаковый тип всех передаваемых объектов; нет прямой связи с буфером команд VDP1.
- Детектор поддерживает только немедленный `JSR @Rn` и специальный вариант с двумя безопасными промежуточными инструкциями; произвольные потоки данных в SH-2 не реконструируются.

## Код и тесты

- `tools/stage32_field_consumer_callers.py`: определяет три пролога через уже проверенный Stage 31, вычисляет адреса BSR, PC-relative MOV.L и сопряжённых JSR, проверяет слоты задержки; в JSON выдаёт только агрегаты.
- `tests/test_stage32_field_consumer_callers.py`: 23 синтетических сценария, включая 12-битное знаковое BSR, выравнивание MOV.L, проверку регистра JSR, передачу R14 через слот задержки, вариант с сохранением R4 на стек и передачей `R5=2`, отрицательные примеры.
- Подлинный ISO не передаётся GitHub Actions и не входит в репозиторий.
