# The Story of Thor 2 — Stage 75: provenance счётчика и runtime service-векторы

## 1. Уточнены два присваивания счётчика перед END-маркером

В Stage74 две записи поля длины оставались неразрешёнными. Теперь подтверждено, что оба вызывающих участка читают одно и то же отдельное поле-счётчик и копируют его 16-битное значение в поле, которое использует callback ID 64.

Внутри основного производителя найдено два локальных пути записи этого исходного поля:

- **Путь A:** в поле записывается R10. В теле производителя R10 явно устанавливается в ноль; до записи отдельного присваивания R10 не обнаружено. Полная сохранность R10 через все вложенные/косвенные вызовы всё ещё требует независимого подтверждения.
- **Путь B:** в поле записывается значение, только что прочитанное через R13 из текущего поля счётчика команд.

Таким образом, эти две записи больше не выглядят как произвольные неизвестные значения: локальная структура сводит их к нулю либо копии текущего счётчика. При этом адреса полей находятся за пределами байтов, загружаемых из файла исполняемого образа, поэтому их начальное значение и порядок первого чтения/записи нельзя восстановить по ISO одному.

## 2. Исправлен ложный вывод о пути сброса счётчика

При повторной проверке Stage74 обнаружена проблема в классификации одного шаблона увеличения: анализатор мог считать более ранний сброс в ноль доказательством для операции, находящейся уже за инструкцией RTS. Исправил анализатор и добавил регрессионный тест, запрещающий переносить доказательство сброса через возврат из функции.

Обновлённая классификация:

- 9 операций увеличения имеют явную проверку CMP/GE с пределом 508 или 460;
- 2 операции увеличения находятся после локального сброса в ноль;
- 1 дополнительный шаблон увеличения отделён от найденного сброса инструкцией RTS и пока не классифицирован как достижимый либо мёртвый код.

Это важная граница доказательства: пока не установлена достижимость третьего шаблона, глобальный верхний предел счётчика **не объявляется доказанным**. Если этот участок недостижим, а локальная передача R10 сохраняет ноль, остальные найденные пути поддерживают инвариант не выше 508 после корректной инициализации.

## 3. Уточнена природа четырёх фиксированных HWRAM-адресов

В исполняемом файле найдено 11 статических ссылок на четыре ранних HWRAM-адреса, используемых для косвенных вызовов. В проверенных локальных окнах не найдено прямой записи в эти адреса сразу после загрузки их адресов.

Уточнение после повторной проверки опкода: один путь загружает адрес в регистр, затем выполняет MOV.L через этот адрес и делает хвостовой JMP по полученному указателю. Это **не** прямой переход к фиксированному адресу. Наблюдаемые пути согласуются с использованием адреса как ячейки runtime-указателя: обычные обработчики вызывают загруженную цель через JSR, а другой участок передаёт управление ей через JMP. Само содержимое указателя и способ его инициализации остаются неизвестными.

Инициализатор этих областей в образе не установлен. Адреса фактических целей вызова остаются значениями из рабочей RAM; без снимка памяти во время выполнения они не разрешаются. Статический поиск не доказывает завершение вызванной функции или завершение DMA.

## 4. Что теперь можно и нельзя утверждать

**Подтверждено статически:**
- два присваивания поля счётчика перед END-маркером читают одно и то же исходное поле;
- у исходного поля обнаружены два локальных пути записи: R10 с локальной инициализацией нулём и копирование текущего счётчика;
- обе статически найденные точки вызова основного производителя следуют за вызовом helper, который сбрасывает счётчик в ноль;
- три варианта обработчика и путь до записи запуска в D0EN остаются подтверждёнными Stage74.

**Пока не доказано:**
- достижимость или недостижимость дополнительного шаблона увеличения рядом с END-helper;
- начальное значение исходного поля до первого подтверждённого обновления и порядок первого чтения/записи;
- сохранение R10 через все вложенные и косвенные вызовы;
- содержимое runtime service-векторов, выбор обработчика в конкретном кадре, событие завершения DMA и синхронизация с submit gate.

## Инструмент и тесты

Добавлен tools/stage75_indirect_services_count_provenance.py. Он объединяет аудит Stage74 с проверкой двух путей записи исходного поля, обоих копирований перед END-маркером, порядка инициализации/вызова производителя и сочетания JSR/JMP через HWRAM service-векторы. Вывод остаётся агрегированным и не раскрывает адреса RAM или смещения кода.

Добавлен tests/test_stage75_indirect_services_count_provenance.py с пятью синтетическими тестами для путей записи, двух копирований, порядка сброса, вызовов service-вектора через указатель и границ заявления об инициализации.

## Следующий этап — Stage76

1. Проследить достижимость дополнительного шаблона увеличения: найти все вычисляемые/табличные переходы, которые могут вести в этот блок, либо доказать, что блок недостижим.
2. Проследить сохранение R10 через весь call-chain, включая косвенные вызовы, чтобы закрыть нулевой путь записи исходного поля.
3. Получить runtime-снимок ранней области HWRAM при запуске игры и определить, кто устанавливает service-векторы и когда это происходит.
4. Только после этого повторно оценить глобальную границу счётчика и подтвердить фактическое завершение DMA по runtime-событию.

**Безопасность данных:** оригинальный ISO, извлечённый исполняемый файл, сырые байты инструкций, runtime-дампы и игровые ресурсы не включены в PR. Отчёт не содержит адресов RAM или смещений кода; запуск и завершение DMA в реальном кадре не заявляются.
