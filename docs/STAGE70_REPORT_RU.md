# The Story of Thor 2 — Stage 70: статусный handshake submit gate

## Результат статического анализа

Уточнено условие запуска transfer submit gate: он проверяет статус как знаковый байт. Если значение неотрицательное, передача не запускается. Если статус отрицательный, gate сначала сбрасывает его в ноль, затем проверяет количество дескрипторов; при нулевом количестве он тоже возвращается, но статус уже сброшен.

В соседнем state-loop найдено место, где статус копируется из байта, полученного через цепочку указателей, после чего вызывается переданный callback. Дополнительный аудит обнаружил функцию, которая явно записывает -1 в тот же статусный байт; указатель этой функции передаётся callback-диспетчеру с ID 64. Сигнатура диспетчера подтверждает запись указателя в таблицу по индексу ID × 4. Это сильный статический кандидат на источник отрицательного перехода, но фактический runtime-вызов и связь именно с этим submit gate ещё не доказаны.

Перед вызовом VDP1 submit gate в одном из путей вызывается отдельная функция, которая читает таблицу записей и пишет в адресные области, соответствующие VDP2 VRAM/CRAM. Это указывает на соседний этап обновления графической памяти, но не доказывает аппаратный порядок или синхронизацию в реальном кадре.

## Переносимая модель

- `begin_transfer_submit()` моделирует знаковую проверку статуса, сброс отрицательного статуса до проверки счётчика и отказ при нулевом количестве.
- Синтетические тесты покрывают положительный, нулевой и отрицательный статус, отрицательный статус с нулевым счётчиком и корректное потребление статуса.
- Проверки используют только искусственные значения; они не запускают оригинальный код и не обращаются к аппаратуре Saturn.

## Дополнительный аудит Stage 70: статусный writer и VDP1

- Найдена одна сигнатура submit gate, 16 PC-relative загрузок указателя общего статусного байта и 10 кандидатов на его запись: одна явная запись -1, три нуля, одна единица и пять значений из неразрешённых регистров.
- Указатель функции с явной записью -1 передаётся callback-регистратору под ID 64. Это подтверждает регистрацию в таблице, но не доказывает, что callback вызывается в момент, нужный submit gate.
- Ограниченный проход по PC-relative указателям распознал 11 16-битных записей в регистры VDP1: TVMR — 3, FBCR — 1, PTMR — 1, EWDR — 2, EWLR — 2, EWRR — 2. Это не полный подсчёт всех ветвей и косвенных указателей.
- В одном пути указатель FBCR (0x25D00002) сдвигается на два байта, после чего в PTMR (0x25D00004) записывается 2. По [руководству Sega VDP1](https://www.infochunk.com/saturn/segahtml_en/hard/vdp1/hon/p04_13.htm), PTMR=2 включает автоматическое рисование на границе кадра; PTMR=1 — ручной запуск при записи. В распознанном пути найден PTMR=2, но не PTMR=1. Это не исключает другие нераспознанные пути.
- Добавлены tools/stage70_vdp1_status_trigger_audit.py и tests/test_stage70_vdp1_status_trigger_audit.py. Шесть синтетических тестов покрывают запись -1, delay slot, регистрацию callback-а, переход указателя FBCR → PTMR, классификацию PTMR=1/2 и отсутствие приватных адресов в сводке.

## Ограничения

Не получена runtime-трасса; статическая регистрация callback-а не подтверждает его фактическое исполнение или причинную связь с submit gate. Порядок завершения VDP2-обновления, копирования данных в VDP1 VRAM и автоматического запуска на границе кадра также не доказан. Оригинальный ISO, исполняемый файл, сырые байты инструкций, приватные адреса и трассы остаются вне PR.

Следующий шаг — проследить runtime-путь вызова callback-а ID 64 и связать обновление FBCR с моментом прохождения submit gate; до этого аппаратная синхронизация остаётся гипотезой.
