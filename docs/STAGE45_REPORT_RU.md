# The Story of Thor 2 — Stage 45: подтверждён SH-2 копировщик 32-байтных команд в VDP1 VRAM

Дата: 22.10.2026. Приватно проверен оригинальный Sega Saturn ISO MK-81302 (SHA-256 `25b0b2774d4621bd9f95a01fc5420ded37b481b61b3cdf515360d82b2cb7bb0d`). Образ, исполняемые байты игры, точные смещения в программе, графические ресурсы и необработанные дампы памяти не размещены в GitHub.

## Проверенный результат

В Stage 44 было подтверждено шесть PC-относительных загрузок адреса VRAM VDP1 `0x25C00000` и три загрузки адреса регистров `0x25D00000`. Stage 45 доказал, что одна из этих загрузок участвует в **конкретной процедуре записи данных в адресное пространство видеопамяти VDP1**.

| Статический признак на оригинальном `0TH2.BIN` | Результат |
|---|---:|
| PC-относительные загрузки базы VRAM VDP1 | **6** |
| Полные распознанные процедуры копирования 32-байтных записей в VRAM | **1** |
| 32-битные записи в одном проходе | **8** |
| Размер переносимой записи | **32 байта** |
| Масштаб исходного 16-битного индекса адреса назначения | **×8** |
| Подтверждённые локальные обратные переходы внутренних/внешних циклов | **2** |
| PC-литеральные косвенные JSR, ведущие к этой процедуре | **1** |

### Адрес назначения

Используя `MOV.L @(disp,PC),R7`, процедура получает базу `0x25C00000`. Затем из записи, на которую указывает входной `R4`, считывает 16-битный индекс. Код делает `EXTU.W`, `SHLL2`, `SHLL` — получает **беззнаковый индекс ×8** — и прибавляет его к базе в `R7`. Результат становится адресом назначения в R1.

После этого из входной записи читается количество внутренних итераций в R2, а исходный адрес данных предварительно считывается в R3. Количество внешних групп берётся из входного R5. Реальные значения этих количеств в игровом сценарии **не наблюдались**.

### Запись 32 байт и повторение

Внутри тела найдено восемь последовательных пар «`MOV.L` из исходного R3 → `MOV.L` в адрес, вычисленный от R1», записывающих смещения `0, 4, 8, 12, 16, 20, 24, 28`. После переноса программа увеличивает исходный и целевой указатели на 32 байта, уменьшает R2 на единицу, сравнивает с нулём и при необходимости возвращается к переносу следующей команды.

Отдельный счётчик R5 уменьшается перед вторым обратным `BF` и выбирает следующую входную запись. Две фактические цели переходов вычислены по знаковым относительным смещениям SH-2, а не угаданы по близости opcode.

В исходном исполняемом модуле подтверждён **один косвенный `JSR`** к точке входа этой функции: адрес загружается в регистр из PC-относительного литерала, рядом выполняется сохранение `R4` на стек и затем `JSR @Rn`. Это означает, что есть конкретная статическая связь между вызывающим кодом и процедурой копирования, но не утверждает, что вызов выполнялся во время игры.

## Что ещё неизвестно

- Нет доказательства, что копировщик вызывается обработчиком №39 из 68-элементной таблицы.
- Не прослежено происхождение исходных командных данных, счётчиков R2/R5 и их семантика.
- Хотя переносится ровно длина одной VDP1-команды, **не получен реальный дамп VRAM или SH-2-трасса**, поэтому нельзя заявить, какие именно команды и при каком игровом событии записываются.
- Не выполнены извлечение и декодирование оригинальных спрайтов, восстановление палитр, графический рендер и компиляция Nintendo Switch NRO.

## Реализация и тесты

- `tools/stage45_vdp1_command_copy.py`: повторно подтверждает аппаратную базу из Stage 44, восемь 32-битных записей, индекс ×8, оба цикла и конкретный входящий косвенный вызов. JSON содержит только агрегаты, никаких адресов исходного исполняемого файла.
- `tests/test_stage45_vdp1_command_copy.py`: **38 синтетических тестов**, охватывающих полный шаблон, повреждение каждого вида записи, источник индекса, сдвиги, регистры, два обратных перехода, PC-литеральный JSR и защиту приватных данных. Локально: **38/38**.
- Оригинальный ISO использовался только приватно. CI проверяет синтетические opcode-макеты и не содержит защищённого кода игры или графики.
