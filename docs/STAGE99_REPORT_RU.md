# The Story of Thor 2 — Stage 99: сохранение R13 между записями control byte

## Источник и приватность

Оригинальный `The Story of Thor 2.iso` повторно получен из приватной папки Google Drive; SHA-256 совпадает с закреплённым значением. В корне ISO 33 файла: 30 payload размером до 5 MiB просканированы полностью, три больших CPK-контейнера пропущены при полном code scan. ISO, extracted payloads, адреса RAM, смещения инструкций и исходные байты не добавлялись в репозиторий.

## Восстановленная последовательность

Повторный анализ подтвердил, что перед второй записью control byte на достижимом пути находятся ровно три вызова и одна условная ветвь. Источник второй записи — `R13`, предварительно установленный в `1`. Сама запись находится в delay slot следующего BSR: запись выполняется до начала вызываемой функции, поэтому этот последующий callee не может изменить значение, которое записывается.

## Аудит трёх предшествующих вызовов

1. **Первый in-image callee:** прямых записей в `R13` не обнаружено, но функция содержит вызов через один низкоадресный pointer slot. Целевой адрес берётся из содержимого слота во время выполнения и отсутствует в образе `0TH2.BIN`. В 30 просканированных root payloads не найдено ни одного точного store-кандидата в этот слот. Сам адрес встречается в коде boot/system area, но это не раскрывает runtime-содержимое слота. Поэтому сохранение `R13` через этот вызов не доказано.

2. **Локальный BSR callee:** обнаружены сохранение `R13` в стек и восстановление перед всеми достижимыми возвратами. Внутренние вызовы не отменяют доказательство, поскольку исходное значение `R13` восстанавливается на выходе. Сохранение `R13` этим callee подтверждено статически.

3. **Loader-wrapper:** сигнатура wrapper-а повторно распознана. На обычном успешном пути оба внутренних helper-а сохраняют `R13`: первый не пишет в регистр напрямую и вызывает только подтверждённые save/restore helpers; второй сохраняет и восстанавливает `R13` перед выходом. Следовательно, нормальный успешный путь wrapper-а сохраняет `R13`. Для отрицательных путей общий error-helper по-прежнему выглядит невозвращающимся по расположению финального dispatcher-а и pointer pool, но runtime-невозвратность не доказана.

## Вывод Stage 99

- При условии, что динамический callee из низкоадресного pointer slot сохраняет `R13` и loader-wrapper возвращается по нормальному успешному пути, вторая запись получает значение `1`.
- Это условный статический вывод, а не безусловное доказательство: runtime-цель низкоадресного pointer slot не разрешена, а возврат из error-helper не подтверждён.
- Все три вызова перед записью идентифицированы; два in-image пути имеют подтверждённое сохранение `R13` на обычных путях, один остаётся неопределённым из-за динамического target-а.

## Реализация и проверки

Добавлен `tools/stage99_callee_register_preservation_audit.py`. Анализатор восстанавливает callsites от caller-derived CFG, распознаёт literal-backed `JSR`, прямые `BSR`, pointer-slot dereference, проверяет dominator-условия для save/restore `R13` и отдельно учитывает delay slot самой записи. Отчёт содержит только агрегированные признаки.

Добавлено семь синтетических тестов: разрешение literal-backed JSR, сохранение неоднозначности pointer slot, разрешение BSR, доминирование восстановления `R13`, выявление незакрытой записи в `R13` и исключение callee из зависимости, когда store находится в его delay slot. GitHub Actions для Stage 99 будет зафиксирован после завершения запуска; CI-успех заранее не заявляется.

## Следующий этап — Stage 100

1. Установить происхождение и runtime-назначение pointer slot через boot/system-area code и, если возможно, проверяемую трассу исполнения; не выводить значение только из ссылки на слот.
2. Проверить, может ли error-helper вернуть управление после финального косвенного dispatcher-а, отдельно от статического признака pointer pool на return address.
3. Если runtime-цель остаётся вне доступных данных, зафиксировать предел доказательства: `R13=1` подтверждается только при оговорённых предпосылках, а не для всех путей.

**Границы вывода:** статически подтверждены три предшествующих вызова, одна условная ветвь и store в delay slot следующего BSR. Второй store равен `1` только при сохранении `R13` динамическим callee из низкоадресного pointer slot и нормальном возврате loader-wrapper-а. Runtime-значение control byte, фактический выбор error-ветвей, overlay execution, callback-регистрация, DMA completion и same-frame graphics timing остаются неподтверждёнными.
