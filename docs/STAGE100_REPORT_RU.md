# The Story of Thor 2 — Stage 100: provenance низкоадресного service slot

## Источник и границы сканирования

Оригинальный ISO прочитан локально; контрольная сумма совпадает с ранее закреплённым значением. В корне найдено 33 файла: 30 payload размером до 5 MiB просканированы полностью, три больших CPK-контейнера исключены из полного code scan. ISO и игровые payloads не добавлялись в репозиторий.

## Что найдено

- Один и тот же низкоадресный slot используется как источник указателя функции в boot/system-area коде, `0TH2.BIN` и `SET07.BIN`.
- В root payloads обнаружено 10 точных PC-relative literal references: 6 в `0TH2.BIN` и 4 в `SET07.BIN`. Из них распознано 10 call patterns `MOV.L @Rn,Rm` → `JSR @Rm` с допустимой подготовкой аргументов между dereference и вызовом.
- В boot/system-area code window найдено ещё одно literal reference и один такой call pattern.
- Ограниченный alias/store scan не нашёл ни одного точного кандидата записи в этот slot среди 30 просканированных root payloads или в исследованном boot-code window.
- Runtime-значение slot и адрес функции, хранящейся в нём, из самого ISO восстановить не удалось. Поэтому его роль как resident service/interface slot — обоснованная гипотеза по повторяющемуся шаблону использования, но не доказанная семантическая идентификация.

## Что это означает для R13

Все три вызова перед второй записью control byte остаются классифицированными как в Stage 99. Один локальный callee явно сохраняет и восстанавливает R13; нормальный успешный путь loader-wrapper также сохраняет R13 через оба helper-а. Единственная неразрешённая зависимость — runtime target низкоадресного slot в первом callee.

Документация Renesas для SuperH C/C++ compiler описывает сохранение и восстановление регистров R8–R14 при соответствующей calling convention; в частности, значения этих регистров считаются неизменными на границе функций, если сохранение/восстановление применяется. Это поддерживает ожидание, что обычный ABI-совместимый target сохранит R13, но не доказывает, что неизвестная runtime-функция соблюдает этот контракт. Источник: [Renesas SuperH RISC engine C/C++ Compiler Package Application Note, section 3.5](https://www.renesas.com/en/document/apn/superh-cc-compiler-package-application-note).

Следовательно, значение `1` во второй записи согласуется со стандартным ABI и всеми подтверждёнными in-image путями, но остаётся условным до определения runtime target либо проверки исполнения. Boot/system-area код тоже обращается к тому же slot, однако в исследованном кодовом окне его инициализатор не найден.

## Реализация и проверки

Добавлен `tools/stage100_low_memory_service_slot_provenance.py`. Он автоматически извлекает slot из уже подтверждённой цепочки Stage 97–99, считает references и pointer-dereference call patterns в root payloads и boot/system-area code window, а также запускает ограниченный поиск записей. JSON содержит только агрегированные значения и не раскрывает адреса, смещения, байты инструкций или игровые данные.

Добавлено пять синтетических тестов: непосредственный вызов после dereference, подготовка аргументов между dereference и JSR, потеря происхождения при перезаписи регистра, точная запись по адресу slot и защита от ложной классификации простого literal reference как вызова. GitHub Actions для Stage 100 будет подтверждён после завершения соответствующего запуска.

## Следующий этап — Stage 101

1. Проверить, есть ли в доступных boot/runtime материалах определение resident slot или таблицы сервисов; не выводить адрес назначения только из ABI.
2. По возможности получить отдельное runtime-свидетельство значения slot и сохранения R13 на этом вызове.
3. Уточнить возврат из общего error-helper-а отдельно от обычного успешного пути wrapper-а.
4. Если runtime-цель остаётся недоступной, оставить значение второй записи условным и не повышать статический вывод до runtime-подтверждения.

**Границы вывода:** общий service-slot pattern подтверждён в boot/system-area коде, `0TH2.BIN` и `SET07.BIN`; ограниченный scan не нашёл его инициализатора в исследованном кодовом окне или 30 root payloads. ABI-ожидание поддерживает сохранение R13, но неизвестный runtime target и поведение error-helper-а остаются неподтверждёнными. Runtime control-byte value, overlay execution, callback registration, DMA completion и same-frame graphics timing не подтверждены.
